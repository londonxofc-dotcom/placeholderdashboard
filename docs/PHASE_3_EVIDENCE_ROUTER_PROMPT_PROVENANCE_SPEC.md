# Phase 3 — Evidence Router + Prompt Provenance Specification

**Status:** DEFINITION MODE — No implementation yet  
**Date:** 2026-04-28  
**Scope:** Evidence validation, prompt lineage, confidence tiers, and routing decisions for memory-assisted reasoning

---

## 1. Canon Boundary

**Phase 2 is complete and locked.** Stages A–G passed all tests (94/94 across 6 modules). Stage H exists as an external current.md checkpoint, not as repo code. Shell-promoter (0448d69) remains KEEP_DEFERRED — not activated, not integrated, not authorized.

**Phase 3 is future and unauthorized.** This specification defines what Phase 3 *will be* if authorized. No code, no database, no API, no UI wiring is part of this document.

## 2. Problem Statement

**The Problem:** When Claude Code or downstream agents reason using memory (Fractal Memory, shell state, Hebbian weights, provenance), they have no visibility into where each piece came from, how confident it is, or whether it contradicts higher-authority sources. A prompt may cite a fact from a stale memory entry, a weak inference, or conflicting evidence without marking the tier.

**Downstream Risk:** Decisions based on mixed-confidence evidence can drift from ground truth. An agent might promote a memory entry that contradicts a verified source. Or block one that contradicts a stale one. Or fail to surface when evidence is conflicted.

**The Gap:** Phase 2 tracks provenance *inside memory* (T0_USER_DIRECT, T1_CANON_LOCKED, etc.). Phase 3 exposes that tracking *to the prompt context* and enforces routing decisions before reasoning begins.

---

## 3. Design Goals

1. **Evidence Visibility:** Every memory fact in the prompt context must be labeled with its source tier and confidence.
2. **Blocking Rules Enforced:** High-authority evidence (canon-locked, user-direct) can block lower-tier facts from entering context.
3. **Drift Prevention:** Conflicting evidence at different tiers triggers a WARN or QUARANTINE decision, not silent override.
4. **Immutability:** Phase 3 does not mutate Phase 2 memory, does not alter retrieval scores, does not change decay behavior.
5. **Auditability:** Every routing decision (ALLOW, WARN, BLOCK) includes a reason_code and explanation string.
6. **Provenance Exposure:** When a fact is allowed into context, its source tier and confidence are visible to the downstream reasoner.

---

## 4. Non-Goals

❌ **Machine learning:** No model retraining, no embedding updates, no learned confidence thresholds.  
❌ **Vector search:** Phase 3 does not change how memory is retrieved.  
❌ **Modifying Phase 2:** No changes to shell graduation, Hebbian weights, decay scheduling, retrieval gates.  
❌ **Database schema changes:** No new tables, no migrations, no schema extensions.  
❌ **UI dashboards:** No visualization of routing decisions.  
❌ **Shell-promoter activation:** That is deferred.  
❌ **Automatic conflict resolution:** Phase 3 flags conflicts, does not resolve them.

## 5. Core Concepts

### Evidence Source Tiers (Canonical)

Each memory fact has a source tier. Higher tiers override lower ones in a routing conflict.

| Tier | Name | Authority | Examples | Override Behavior |
|------|------|-----------|----------|-------------------|
| T0 | USER_DIRECT | Highest | User explicitly stated in current.md, in a session prompt, or in a direct instruction | Blocks all lower tiers |
| T1 | CANON_LOCKED | High | Committed at a canonical tag (e.g., `oracle-phase-2-docs-canon-locked`), passed all tests, no drift | Blocks T2–T5 |
| T2 | VERIFIED_MODULE | Medium | Passed unit/integration tests, part of a committed module, but not canon-locked | Blocks T3–T5 |
| T3 | SCAFFOLD | Medium-Low | Generated by Phase 2, verified by rules but not by tests (e.g., Hebbian co-occurrence weights) | Blocks T4–T5 |
| T4 | INFERENCE | Low | Derived from patterns in memory, not explicitly stored (e.g., "user prefers concise answers" inferred from recent interactions) | Blockable by T0–T3 |
| T5 | UNTRUSTED | Lowest | User input, external API data, unvalidated sources | Blockable by all higher tiers |

### Confidence Labels (Canonical)

Each memory fact has a confidence label. Independent of source tier.

| Label | Meaning | Examples |
|-------|---------|----------|
| VERIFIED | Fact has been tested, validated, or explicitly confirmed by user | Test passed, user said "yes", canonically tagged |
| LIKELY | Fact is supported by strong evidence but not verified | 18/18 Hebbian tests pass, weight ≥ 0.8 |
| INFERRED | Fact is derived from patterns; plausible but not proven | Hebbian weight ≥ 0.5, or user behavior suggests a pattern |
| STALE | Fact was true, but evidence is old (>30 days inactive) | Entry in decay_state = "stale" or "archive_candidate" |
| CONFLICTED | Fact contradicts another fact at a higher tier or confidence | T1 says X, T4 says ¬X; or VERIFIED contradicts INFERRED |
| UNVERIFIED | Fact has not been tested or validated | New entry, not yet promoted, no supporting evidence |
| BLOCKED | Fact is quarantined or explicitly excluded by a rule | quarantine_status = "quarantined", or rule_activation = "BLOCK" |

## 6. Evidence Source Tiers — Detailed

### T0: USER_DIRECT
- **What qualifies:** User statement in current.md, session prompt, explicit instruction, or signed approval in a checkpoint
- **Validation:** None required; user statement is final
- **Confidence:** Always VERIFIED (user said it)
- **Routing:** Blocks all lower tiers if in conflict
- **Example:** User writes in current.md: "Vampire Sex + Hotboxx is the primary focus this session" → T0_USER_DIRECT, VERIFIED, blocks any T1–T5 inference that contradicts it
- **Phase 2 Connection:** Stored in current.md (16D), linked to task/context/decisions roles

### T1: CANON_LOCKED
- **What qualifies:** Committed at a stable tag (e.g., `oracle-phase-2-docs-canon-locked` → 115d8af), passed all Phase 2 tests, no drift detected
- **Validation:** Tag must exist, commit must be on main or a protected branch, tests must pass at that commit
- **Confidence:** Typically VERIFIED, may be LIKELY if tests pass but coverage is not 100%
- **Routing:** Blocks T2–T5 if in conflict
- **Example:** PHASE_2_STAGE_G_EVAL_REPORT.md at 115d8af states "94/94 tests pass" → T1_CANON_LOCKED, VERIFIED, blocks any T4 inference that says tests fail
- **Phase 2 Connection:** Stored in `docs/` committed at canon tag; immutable

### T2: VERIFIED_MODULE
- **What qualifies:** Part of a committed module (e.g., retrieval-gate-integration.ts) with passing unit/integration tests but not canon-locked
- **Validation:** Tests must pass in the module, coverage ≥80%, no TODOs or FIXMEs blocking the logic
- **Confidence:** VERIFIED if 100% coverage, LIKELY if 80–99% coverage, INFERRED if draft but tests pass
- **Routing:** Blocks T3–T5 if in conflict
- **Example:** retrieval-gate-integration.ts at commit abc1234 has 20/20 tests passing → T2_VERIFIED_MODULE, VERIFIED, blocks T4 inference that contradicts retrieval gate logic
- **Phase 2 Connection:** Lives in `ui/lib/oracle/`, tests in `ui/lib/oracle/__tests__/`, both committed

### T3: SCAFFOLD
- **What qualifies:** Generated by Phase 2 rules (e.g., Hebbian weights, decay state transitions, anchor status) that are rule-checked but not test-covered in isolation
- **Validation:** Must come from a Phase 2 module with passing tests (e.g., hebbian-dynamics.ts passes, so its output weights are T3)
- **Confidence:** LIKELY (rules are rule-checked) or INFERRED (rules are probabilistic)
- **Routing:** Blocks T4–T5 if in conflict
- **Example:** Hebbian weight for (VS, LEARNING) = 7.2 from a session where both codes activated → T3_SCAFFOLD, LIKELY (hebbian-dynamics tests pass), blocks T4 inference that says the pair shouldn't co-load
- **Phase 2 Connection:** Generated by hebbian-dynamics, decay-scheduler, shell-graduation modules during retrieval or promotion

### T4: INFERENCE
- **What qualifies:** Derived from patterns in memory without explicit storage (e.g., "user prefers fast answers" inferred from 5 recent sessions of short outputs)
- **Validation:** Must cite the evidence it was inferred from (e.g., "inferred from 5 sessions with <100 words output")
- **Confidence:** INFERRED (by definition), may degrade to STALE if evidence is old, CONFLICTED if contradicted by T0–T3
- **Routing:** Blockable by T0–T3 if in conflict
- **Example:** "User favors London X over Vampire Sex content" inferred from session history → T4_INFERENCE, INFERRED, blocked by user statement in T0 that prioritizes Vampire Sex this session
- **Phase 2 Connection:** Lives in local anchors, Hebbian adjacencies, role-pair weights; generated on retrieval, not stored long-term

### T5: UNTRUSTED
- **What qualifies:** User input not yet validated, external API responses, unvetted third-party data, or memory entries with missing provenance
- **Validation:** Must be validated against T0–T3 sources before promotion
- **Confidence:** UNVERIFIED (by definition), BLOCKED if it contradicts a higher tier
- **Routing:** Blockable by all higher tiers
- **Example:** External API returns "Vampire Sex has 3M streams" but Phase 2 canon says 2.71M → T5_UNTRUSTED, UNVERIFIED, CONFLICTED with T1_CANON_LOCKED — router must flag for manual review
- **Phase 2 Connection:** Enters via shell-promoter or external integrations; must cite provenance before promotion

## 7. Confidence Labels — Detailed

### VERIFIED
- **Definition:** Fact has passed tests, been explicitly confirmed by user, or is canonically tagged
- **Triggering conditions:**
  - Passed 100% of relevant tests (unit/integration/end-to-end)
  - User explicitly said "yes" or approved in a checkpoint
  - Committed at a stable tag
  - Phase 2 module with no open TODOs blocking the logic
- **Routing:** Can be used as evidence to block CONFLICTED or INFERRED facts
- **Example:** "retrieval-gate-integration passes 20/20 tests" → VERIFIED

### LIKELY
- **Definition:** Fact is supported by strong evidence but not explicitly verified
- **Triggering conditions:**
  - Test coverage 80–99%
  - Hebbian weight ≥ 0.8 with ≥3 sessions of co-occurrence
  - Multiple corroborating sources at T1–T3
- **Routing:** Can be used to downgrade INFERRED or STALE facts in conflict
- **Example:** "Hebbian weight for (VS, BUILDS) = 0.85 across 5 sessions" → LIKELY

### INFERRED
- **Definition:** Fact is derived from patterns; plausible but not proven
- **Triggering conditions:**
  - Derived from ≥3 data points but <100% coverage
  - Hebbian weight 0.5–0.8 or ≥2 sessions of co-occurrence
  - No contradicting T0–T2 evidence
- **Routing:** Can be blocked by T0–T3 evidence
- **Example:** "User works best with one task at a time" inferred from 4 recent sessions with feedback on task stacking → INFERRED

### STALE
- **Definition:** Fact was true, but evidence is old and may have changed
- **Triggering conditions:**
  - Memory entry in decay_state = "stale" or "archive_candidate"
  - Last observation >30 days ago
  - No refresh or confirmation since that date
- **Routing:** Lower priority in conflicts; marked for manual review if contradicted by fresher evidence
- **Example:** "User prefers Pro Tools" observed 90 days ago, no recent confirmation → STALE

### CONFLICTED
- **Definition:** Fact contradicts another fact at a higher tier or stronger confidence
- **Triggering conditions:**
  - T4 says X, T1 says ¬X
  - INFERRED says X, VERIFIED says ¬X
  - Two T3 facts contradict each other
- **Routing:** Triggers WARN or QUARANTINE decision; cannot enter context without user arbitration
- **Example:** T4 inference "user favors Ableton" contradicts T0_USER_DIRECT "I prefer Logic" → CONFLICTED, must WARN or QUARANTINE

### UNVERIFIED
- **Definition:** Fact has not been tested or validated
- **Triggering conditions:**
  - New memory entry, not yet promoted
  - No supporting test evidence
  - No user confirmation
- **Routing:** Can be blocked by T0–T4 evidence; low priority in conflicts
- **Example:** "Niko product roadmap includes video generation" not yet tested or approved → UNVERIFIED

### BLOCKED
- **Definition:** Fact is explicitly quarantined or excluded by a rule
- **Triggering conditions:**
  - quarantine_status = "quarantined" in Phase 2 metadata
  - rule_activation = "BLOCK" fired before retrieval
  - Explicit denial in T0_USER_DIRECT
- **Routing:** Cannot enter context under any condition; flagged for manual review only
- **Example:** Memory entry flagged as "do not use until IP cleared" → BLOCKED

## 8. Routing Decision Model

The Evidence Router evaluates each memory candidate against the incoming prompt context and issues a decision: ALLOW, ALLOW_WITH_LABEL, WARN, QUARANTINE, or BLOCK.

### Decision Outcomes

| Decision | Meaning | Action | Next Step |
|----------|---------|--------|-----------|
| ALLOW | Fact is permitted to enter prompt context with full confidence | Include in context, no labels | Use normally in reasoning |
| ALLOW_WITH_LABEL | Fact is permitted but must be labeled with source tier and confidence | Include in context with provenance metadata | Downstream reasoner sees the tier and adjusts confidence |
| WARN | Fact has issues (stale, conflicted, or low confidence) but is not blocked | Include in context, flag as ⚠️ WARN, include explanation | Downstream reasoner can use but should prioritize alternatives |
| QUARANTINE | Fact may be harmful or contradicts critical evidence; human review needed | Do not include in context, log for review, suggest alternatives | User or operator reviews and makes final decision |
| BLOCK | Fact is explicitly forbidden or violates a hard rule | Do not include in context, do not log, remove from scope | Never use, audit log only |

### Routing Decision Tree

```
FOR EACH memory_candidate:

1. Is quarantine_status = "quarantined" OR rule_activation = "BLOCK"?
   → BLOCK (hard stop, never override)

2. Is source_tier = T0_USER_DIRECT AND confidence = VERIFIED?
   → ALLOW (user statement, highest authority)

3. Is source_tier = T1_CANON_LOCKED?
   → ALLOW if no conflict with T0
   → ALLOW_WITH_LABEL if confidence < VERIFIED
   → WARN if STALE (but still canon)
   → QUARANTINE if CONFLICTED with T0

4. Is source_tier = T2_VERIFIED_MODULE OR T3_SCAFFOLD?
   → ALLOW if confidence = VERIFIED and no higher-tier conflict
   → ALLOW_WITH_LABEL if confidence = LIKELY or INFERRED
   → WARN if STALE or CONFLICTED with T0–T1
   → QUARANTINE if CONFLICTED with T0 and no T2+ support
   → BLOCK if explicitly denied in T0

5. Is source_tier = T4_INFERENCE?
   → ALLOW_WITH_LABEL if no T0–T2 conflict
   → WARN if STALE or CONFLICTED with T0–T3
   → QUARANTINE if directly contradicts T0–T2
   → BLOCK if explicitly denied in T0

6. Is source_tier = T5_UNTRUSTED?
   → ALLOW_WITH_LABEL only if validated against T0–T3
   → WARN if unvalidated
   → QUARANTINE if CONFLICTED
   → BLOCK if contradicts T0 or marked as untrusted
```

### Routing Rules (Non-Negotiable)

1. **T0 Override Rule:** Any T0_USER_DIRECT, VERIFIED fact blocks all lower tiers if they conflict.
2. **Canon Lock Rule:** Any T1_CANON_LOCKED fact with VERIFIED confidence cannot be overridden by T2–T5.
3. **Conflict Rule:** If two facts at the same tier conflict (e.g., two T3 Hebbian weights), mark as CONFLICTED and WARN or QUARANTINE.
4. **Immutability Rule:** The routing decision does not mutate the underlying memory. It only controls what enters the prompt context.
5. **Explainability Rule:** Every decision must include a reason_code and explanation_string. No silent filtering.

// Evidence source tier (canonical)
type SourceTier = "T0_USER_DIRECT" | "T1_CANON_LOCKED" | "T2_VERIFIED_MODULE"

  conflicting_fact_id?: string

  // Audit trail
  applied_rules: string[]

  }

  timestamp: string
  
  // The incoming prompt + active domain
  user_query: string
  active_domain: string
  
  // Memory facts with provenance

    total_facts: number
    allowed_count: number
    allowed_with_label_count: number
    warned_count: number
    quarantined_count: number

  }
  
  // Audit trail

    evaluated_at: string
    evaluation_duration_ms: number
    rules_applied: string[]
    conflicts_detected: number
    conflicts_detail: Array<{ fact_a: string; fact_b: string; reason: string }>
  }

## 10. Integration with Phase 2 — Immutable

**Phase 2 is read-only. Phase 3 does not change Phase 2 behavior.**

- **Retrieval Gate (Stage F):** Phase 3 does not modify the retrieval gate. The gate continues to filter candidates and compute confidence as designed in Phase 2. Phase 3 sits *downstream* of the gate, labeling facts that the gate permits.
- **Shell Graduation (Stage B):** Phase 3 does not affect promotion decisions. Shell graduation continues to apply its 4-state decision enum (promote | hold | quarantine | reject). Phase 3 only labels the resulting promoted facts.
- **Hebbian Dynamics (Stage D):** Phase 3 does not alter weight accumulation or decay. Hebbian weights continue to be computed as designed. Phase 3 only labels them with source tier T3 and confidence LIKELY.
- **Decay Scheduler (Stage E):** Phase 3 does not change state transitions or quarantine behavior. Decay continues as designed. Phase 3 only marks stale/archive facts with confidence label STALE.
- **Anchor Promotion (Stage C):** Phase 3 does not affect anchor status or boost logic. Anchors continue to work as designed. Phase 3 only labels them as source tier T3, confidence LIKELY.
- **Rule Activation Monitor (custom module):** Phase 3 respects BLOCK and QUARANTINE activations from rules. BLOCKED facts are marked as BLOCKED, QUARANTINED facts are quarantined. No override.

**Connection point:** The Evidence Router runs on the output of the Retrieval Gate. It takes allowed/downgraded/blocked candidates, labels them with provenance and confidence, and decides whether to include them in the prompt context.

## 11. Drift-Control Rules

These rules prevent Phase 3 from mutating, overriding, or destabilizing Phase 2.

### Rule 1: Read-Only Phase 2
- Phase 3 never writes to Phase 2 state
- No mutations to memory entries, decay state, Hebbian weights, or anchor status
- No changes to shell graduation decisions
- No modifications to rule activations
- **Verification:** Git diff after Phase 3 implementation must not touch any `ui/lib/oracle/` files except the new router module

### Rule 2: Labeling Only
- Phase 3 adds labels (source tier, confidence, reason codes) but does not change facts
- A fact labeled STALE is still usable at T3 confidence; Phase 3 does not delete it
- A fact labeled CONFLICTED is still visible; Phase 3 flags it for review but does not hide it
- **Verification:** Proof of immutability: JSON.stringify(original_fact) === JSON.stringify(labeled_fact) after removing label fields

### Rule 3: Provenance Completeness
- Every memory fact entering the Evidence Router must have a source tier and confidence label
- If a fact cannot be assigned a tier (missing provenance), it defaults to T5_UNTRUSTED
- **Verification:** 100% of facts in the routing decision must have non-null source_tier and confidence_label

### Rule 4: Conflict Transparency
- If a conflict is detected, it must be logged and reported to the user, never silently overridden
- CONFLICTED facts must be marked as such in the routing decision
- **Verification:** All CONFLICTED decisions include a reason_code that names the conflicting fact

### Rule 5: Blocking Precedence
- BLOCK decisions are absolute and have highest precedence
- No labeling, no warning, no override — BLOCK is final
- **Verification:** Zero BLOCKED facts ever appear in the allowed_facts list

### Rule 6: No Leakage Between Domains
- Evidence from domain A should not bleed into domain B unless explicit_cross_domain_reason is set
- Source tier and confidence are domain-local; adjacency does not grant authority
- **Verification:** Cross-domain facts in the output include explicit_cross_domain_reason or are marked WARN

## 13. Example Scenarios

### Scenario 1: T0 Blocks T4 on Focus Conflict
**Situation:** User writes in current.md: "Focus: Vampire Sex this session." Later, a T4_INFERENCE retrieves: "User prefers London X content over Vampire Sex."

**Router evaluation:**
- T0_USER_DIRECT (current.md statement) = "Focus: Vampire Sex"
- T4_INFERENCE = "User prefers London X"
- Conflict detected: T4 contradicts T0

**Decision:** BLOCK

**Reason codes:** ["t0_overrides_t4", "contradicts_user_direct"]

**Explanation:** "T0_USER_DIRECT explicit focus (Vampire Sex) blocks T4_INFERENCE (London X preference). T0 takes precedence."

---

### Scenario 2: STALE Warning with T1 Canon Support
**Situation:** Phase 2 canon says "Vampire Sex has 2.71M Spotify streams" (T1, VERIFIED, from 115d8af). A local anchor stores "Vampire Sex streams = 2.5M" from 60 days ago.

**Router evaluation:**
- T1_CANON_LOCKED (115d8af) = 2.71M, VERIFIED
- T3_SCAFFOLD (local anchor, 60 days stale) = 2.5M, STALE
- No direct contradiction if treating both as estimates, but staleness is clear

**Decision:** ALLOW_WITH_LABEL (both allowed, T1 ranked higher)

**Reason codes:** ["age_factor_downgrade", "canon_lock_takes_precedence"]

**Explanation:** "T1_CANON_LOCKED fact (2.71M, VERIFIED) is fresh; T3_SCAFFOLD fact (2.5M, STALE, 60 days) is permitted but marked for refresh."

---

### Scenario 3: CONFLICTED Evidence — Manual Review Required
**Situation:** T2_VERIFIED_MODULE retrieval-gate-integration.ts says: "Quarantine blocks all candidates." Later, a T4_INFERENCE from session history says: "Quarantine can be overridden by user appeal."

**Router evaluation:**
- T2_VERIFIED_MODULE (retrieval-gate-integration, 20/20 tests) = "Quarantine blocks all"
- T4_INFERENCE (5-session pattern) = "Quarantine can be overridden"
- Direct contradiction

**Decision:** QUARANTINE (both facts held for review)

**Reason codes:** ["t2_t4_conflict", "policy_contradiction"]

**Explanation:** "T2_VERIFIED_MODULE (hard rule: quarantine blocks all) contradicts T4_INFERENCE (user can appeal). Conflicting policies detected. Both facts held; manual review required to determine canonical behavior."

---

### Scenario 4: UNVERIFIED Input Rejected Pending Validation
**Situation:** External API returns: "Reefro Cons is no longer with Vampire Sex." This is T5_UNTRUSTED with no supporting evidence in Phase 2 canon.

**Router evaluation:**
- T5_UNTRUSTED (external API) = "Reefro Cons departed"
- No T0–T3 fact supports or refutes this
- No validation against canon

**Decision:** BLOCK (until validated)

**Reason codes:** ["untrusted_unvalidated", "major_claim_no_canon_support"]

**Explanation:** "T5_UNTRUSTED fact (external API) claims major personnel change. No T0–T3 validation found. Blocked pending manual verification against canon sources."

---

### Scenario 5: ALLOWED with T3 Label and Confidence Downgrade
**Situation:** Hebbian weight for (BUILDS, LEARNING) is 0.62 from 3 sessions. No explicit user statement; no canon. Enters retrieval gate successfully (weight ≥ 0.5). Now Phase 3 labels it.

**Router evaluation:**
- T3_SCAFFOLD (Hebbian, hebbian-dynamics tests pass) = 0.62
- Confidence: weight 0.62 → INFERRED (not quite LIKELY threshold of 0.8)
- No conflict with T0–T2
- Stale? No, 3 recent sessions

**Decision:** ALLOW_WITH_LABEL

**Reason codes:** ["t3_scaffold_no_conflict"]

**Explanation:** "T3_SCAFFOLD Hebbian weight (0.62) from 3 sessions, confidence INFERRED. Allowed with label. Downstream reasoner should treat (BUILDS, LEARNING) co-load as plausible but not certain."

## 14. Open Questions

1. **Prompt Injection Risk:** If a user or downstream agent writes a T0 statement that is itself adversarial (e.g., "Ignore all rules"), how does Phase 3 validate the statement before granting T0 authority?
   - *Tentative answer:* Phase 3 assumes current.md is Nick-written and trusted. If current.md is co-written or comes from an untrusted source, those claims are T5 until validated.

2. **Cross-Domain Confidence Decay:** If (BUILDS, LEARNING) has a Hebbian weight from Ring 1, but the user queries in the AGENCY domain (Ring 3 from BUILDS), should confidence degrade?
   - *Tentative answer:* Ring distance affects retrieval gate confidence, not source tier. Phase 3 applies ring-based confidence modifiers on top of source tier labels.

3. **Conflict Resolution Hierarchy:** When T1 contradicts T4, and T4 is supported by recent evidence, should Phase 3 ever allow both into context with a WARN instead of QUARANTINE?
   - *Tentative answer:* If both are important (e.g., canon says X, recent experience suggests ¬X), WARN + both facts is more transparent than QUARANTINE alone. User sees the conflict and can decide.

4. **Stale Refresh:** If a T3_SCAFFOLD fact is marked STALE, what triggers a refresh? Is there a background process, or does it require explicit user action?
