## 3. Why RI-5 Needs A Scope Proposal

RI-5 is the first stage that may approach a live runtime boundary. RI-3 implemented the pure pipeline function and RI-4 locked fixture tests against that function, but neither stage authorizes live input, live Evidence Router output, app routes, UI triggers, persistence, storage writes, background jobs, or autonomous forecasts.

RI-5 must be scoped before code begins because the phrase "runtime pipeline wiring" can drift into several forbidden surfaces:

- live Evidence Router consumption
- public API routes
- UI trigger buttons
- persistence and audit storage
- background execution
- autonomous forecast generation
- modifications to locked model, bridge, kernel, or audit files

This proposal narrows RI-5 to an approved wiring boundary before implementation.

## 4. Relationship To RI-2 Type Contracts

RI-2 defines the active runtime pipeline input and result contracts:

- `RuntimePipelineInput`
- `RuntimePipelineResult`
- `RUNTIME_PIPELINE_RESULT_STATUSES`

RI-5 must preserve the RI-2 invariants:

- all caller-supplied fields remain required
- no supplemented field is defaulted, inferred, or generated by runtime wiring
- only `status: success` may carry non-null `forecast` and `auditEntry`
- every failure branch carries `forecast: null` and `auditEntry: null`
- no `partial_success`
- no queue/defer result state

The older runtime integration gate spec uses pre-RI-2 names such as `RuntimeIntegrationRequest`, `RuntimeIntegrationResult`, and `runPredictabilityPipeline`. RI-5 must not reintroduce those names unless a new ratified contract explicitly replaces RI-2. The active names are the RI-2/RI-3 names.

## 5. Relationship To RI-3 Runtime Pipeline Function

RI-3 implemented:

- `runPredictabilityRuntimePipeline(input: RuntimePipelineInput): RuntimePipelineResult`

The function executes the locked five-step sequence:

1. Bridge adapter input to kernel-native input.
2. Calculate the predictability forecast.
3. Create a forecast audit entry.
4. Validate the forecast audit entry.
5. Assert audit safety flags.

RI-5 must treat this function as the approved pure runtime pipeline surface. RI-5 may call this function from a narrow invocation boundary if separately authorized, but RI-5 must not modify the function unless a new explicit authorization allows a specific change.

The older runtime integration gate spec references `BridgeResult.bridgeStatus`. RI-3 corrected this: the codebase uses `bridgeResult.success` on `BridgeResult`, while `bridgeStatus` lives inside `bridgeResult.bridgeContract`. RI-5 implementation must follow the RI-3 function and type contracts, not the stale wording.

## 6. Relationship To RI-4 Fixture Tests

RI-5 must not weaken or bypass RI-4 coverage. Any RI-5 implementation must add its own tests without deleting, weakening, or rewriting RI-4 fixture tests.

## 7. Definition Of RI-5 Runtime Wiring

For this proposal, RI-5 runtime wiring means creating or defining a narrow invocation boundary that can supply a fully formed `RuntimePipelineInput` to `runPredictabilityRuntimePipeline` under controlled conditions.

RI-5 runtime wiring does not mean public app exposure, autonomous execution, or persistence.

The approved RI-5 concept is:

```text
approved runtime invocation boundary
  -> fully formed RuntimePipelineInput
  -> runPredictabilityRuntimePipeline(input)
  -> RuntimePipelineResult
  -> caller receives typed result
```

RI-5 must preserve the current fail-closed contract. If required input cannot be supplied without violating a locked boundary, the invocation boundary must stop before calling the pipeline.

## 10. Required Inputs

Any RI-5 invocation boundary must require a complete `RuntimePipelineInput`:

- `objective`
- `targetDate`
- `domain`
- `horizon`
- `trendWindows`
- `behavioralPatterns`
- `cycleWindows`

The invocation boundary must not default, infer, or generate missing input.

If any required field is absent, unavailable, empty, or outside the expected shape, RI-5 must stop before invocation or produce the existing fail-closed result behavior through the pipeline contract.

## 11. Required Outputs

The only approved output from the runtime pipeline surface is `RuntimePipelineResult`.

Allowed result statuses remain:

- `success`
- `bridge_failed`
- `audit_creation_failed`
- `audit_validation_failed`
- `safety_flag_failed`

RI-5 must not introduce:

- queued status
- deferred status
- partial success
- background status
- incomplete audit success
- persistence success

## 12. Failure Behavior

RI-5 must preserve RI-2/RI-3 failure behavior:

- bridge failure returns `bridge_failed`
- audit creation failure returns `audit_creation_failed`
- audit validation failure returns `audit_validation_failed`
- safety flag failure returns `safety_flag_failed`
- every failure branch returns `forecast: null`
- every failure branch returns `auditEntry: null`

No forecast may be surfaced from any failure branch.

## 13. Safety And Fail-Closed Requirements

RI-5 must fail closed at every boundary:

- missing input means no runtime execution
- invalid input means no runtime execution or a typed fail-closed pipeline result
- bridge failure means no kernel result surfacing
- audit creation failure means no forecast surfacing
- audit validation failure means no forecast surfacing
- safety flag failure means no forecast surfacing

RI-5 may not catch an error and continue with partial output.

## 14. Audit Requirements

RI-3 currently creates and validates an audit entry and marks success with:

- `persistenceState: persisted_by_future_gate`

RI-5 must not convert this marker into a storage write without separate authorization.

If RI-5 creates an invocation boundary, it must preserve the audit entry returned by `runPredictabilityRuntimePipeline` and must not strip, rewrite, or persist it.

Any future audit persistence decision requires a separate packet.

## 15. Test Requirements

A future RI-5 implementation packet must include tests for:

- valid invocation boundary with complete fixture input
- missing required scalar field stops or fails closed
- missing required array field stops or fails closed
- empty required array fails closed
- no defaulting of `targetDate`
- no defaulting of `domain`
- no defaulting of `horizon`
- no direct kernel call outside `runPredictabilityRuntimePipeline`
- no queued/deferred/partial status introduction
- failure result carries `forecast: null` and `auditEntry: null`

Tests must be fixture-based unless a separate packet authorizes live Evidence Router input.

## 17. Drift Risks

- using stale gate-spec names instead of RI-2/RI-3 names
- reading or relying on protected memory context

- weakening RI-4 fixture tests
